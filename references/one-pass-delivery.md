# 一遍过交付：建模 / 命令方块 / 导入 / 实测

> 结论先说：**功能、结构、实体、物品、tag、性能可以做到“基本一遍过”**；**客户端视觉（FMBE 偏移、模型比例）不能保证像素级一遍过**，因为无头 bot 看不到客户端画面，需要一张截图做最后校准。
> 这份清单来自两次真实交付：雪球三级菜单（256 方块）和 FMBE 1:1 玩家（6 部件）。

## 1. 先定义“过”的标准

| 层级 | 一遍过的标准 | 能否保证 |
|---|---|---|
| 命令语法 | 全部能在网易 1.21.130 解析 | 可以 |
| 结构导入 | 方块数量/类型/朝向正确 | 可以（加 repair） |
| 实体/物品 | 6 个部件都在、tag/物品正确 | 可以 |
| 状态机 | 页面/开关/重置路径可走通 | 可以 |
| 性能 | 不因 20 Hz 长链把服务器拖超时 | 可以（限频） |
| UI 文本 | actionbar 正常、不超 512 字节、不弹大标题 | 可以 |
| 客户端视觉 | 模型对齐、不漂浮、比例正确 | **需要截图校准一轮** |

## 2. 生成前：把“执行位置”想清楚

这是 FMBE 实测最大的坑：

```mcfunction
# 错：命令方块在 y=210，r=1 是相对命令方块，不是相对模型
tag @e[type=fox,r=1] add pm_head

# 对：用绝对体积选择器圈住展示区
tag @e[type=fox,x=69,y=1,z=7,dx=2,dy=3,dz=2] add pm_head
```

规则：

- 命令方块远离展示区时，**不要用 `r/rm` 选展示实体**；用 `x/y/z/dx/dy/dz`。
- `execute positioned <展示原点>` 也可以把 `r` 的基准挪过去。
- 每个选择器都问一句：**它相对谁？** 命令方块、玩家、还是 `execute positioned`。

## 3. 生成前：把实体/命令的数量压下来

| 坑 | 实测后果 | 正确做法 |
|---|---|---|
| FMBE 48 条 Molang × 20 Hz | 服务器命令超时、聊天延迟、`hasitem` 超时 | 初始化一次 + **1 Hz 刷新** |
| 6 只狐狸不锚定 | 狐狸走散，模型散架 | 单独一条 repeat：每 tick `tp` 到原点 |
| 长链横跨 9 区块 | 必须 tickingarea，24h 空转 | 蛇形压缩到 **1 个区块柱** |
| 每 tick `titleraw @a` | 刷屏/带宽 | actionbar 5~10 Hz，按需显示 |
| 每个功能一个 repeat 头 | 20 Hz 爆 | 一个 repeat 头 + 一条 chain |

## 4. 生成前：命令文本与 UI

- 普通 `title` 纯文本约 **512 字节**会静默失败；大面板用 `titleraw`。
- 不要每次交互弹 `title @s title` 大标题；菜单用 `actionbar`。
- 动作组用 **`sbg`/组 id** 防“第一条命令改了状态，后面同组命令全部失效”的级联 bug。
- 旧 `execute @a ~ ~ ~` 一律升级 `execute as @a at @s run ...`。
- 单条命令 < 32,500 字符；长 Molang 拆成多条 `playanimation`。

## 5. 导入：BuildTask 之后必须 repair

实测：BuildTask 会偶发漏 NBT/漏启用，表现为“方块存在但命令是空的/不跑”。

固定流程：

1. `fill` 清掉旧结构（按新结构包围盒，不只清一层）。
2. `BuildTask`：
   - `UseFillBuildMode=false`
   - `AutoDisableCommand=false`
   - `VerifyChunkLevel=1`
3. **逐块 `CommandBlockUpdate` 回写**命令/NBT/延迟/模式。
4. 校验：方块总数、类型、朝向、repeat 头数量。
5. 再跑功能测试。

> 没有 repair 的导入只能算“方块摆好了”，不能算“命令生效了”。

## 6. 实测：先测“有没有”，再测“对不对”

| 顺序 | 测试 | 例子 |
|---|---|---|
| 1 | 实体数量 | `execute as @e[tag=pm_model] run scoreboard players add pm_count pm 1` → 6 |
| 2 | tag/物品 | `hasitem={item=player_head,...}` 四项全过 |
| 3 | 位置 | `querytarget` 都在 `70.5 2 8.5` |
| 4 | 状态 | `pm_init=1`，`pm_render=1` |
| 5 | 性能 | 命令不超时、聊天不延迟 |
| 6 | UI 包 | 监听 `SetTitle`，确认只有 actionbar（ActionType=4），无 title/subtitle |
| 7 | 视觉 | 截图看比例/偏移 |

## 7. 实测踩过的具体坑

### FMBE

- `summon fox ... minecraft:as_adult "name"` 在网易实测会卡住/超时；用**普通 summon + tag**，不要 name/event 参数。
- 头物品实际是 `player_head`（`skull 3` 给出来），`hasitem` 要查 `player_head`，查 `skull` 会 false。
- `r=1` 是命令方块位置，不是模型位置；用体积选择器。
- 一次性渲染可能不保持姿势；**1 Hz 刷新** + 每 tick 锚定，兼顾稳定与性能。
- 多部件模型**一个部件一只狐狸，站在部件中心**；不要堆在同一点靠 `v.pos` 偏移，否则头/身体会前后错位。
- 整数 `summon` 坐标会吸到 `.5`，小数坐标不会；统一用真实中心，避免左右不对称。
- 普通版写 `xzscale/yscale`，EX 版写 `extend_scale/extend_xrot`；同一命令两组都写。
- 无头 bot 只能验证实体/物品/tag，不能看客户端模型；视觉必须截图校准。

### 雪球菜单

- 行动组级联：`sbm` 一改，后面的原状态选择器失效；用 `sbg` 组 id。
- 大标题多余：删除 `title/subtitle/times`，只留 actionbar。
- 宽版 167 格跨 9 区块；蛇形压缩到 15×6×9。
- BuildTask 漏 NBT；必须逐块 repair。
- UI 文本 459 字节接近 512 上限；再长就换 `titleraw` 或拆行。

## 8. “一遍过”生成协议

下一次给模型/系统，按这个顺序做：

1. **表**：部件/页面/状态全部列成表（tag、物品、尺寸、偏移、命令）。
2. **预算**：实体数、命令数、刷新 Hz、区块数、是否要 tickingarea。
3. **生成器**：数据驱动，不手写重复命令；蛇形紧凑布局。
4. **静态检查**：链头/链尾、朝向、条件、命令长度、选择器基准。
5. **导入 + repair + 校验**。
6. **服务器功能测试**：数量、tag、物品、位置、状态、性能、UI 包。
7. **视觉校准**：用户一张截图；只调偏移/缩放，不动逻辑。
8. **回归**：重置链能回到初始状态；旧结构已清；无 tickingarea 空转。

## 9. 诚实的结论

- **同类模型/菜单再做一个**：结构、命令、实体、物品、tag、性能可以**基本一遍过**。
- **视觉像素级一遍过**：不能保证；FMBE 的物品原点/缩放是客户端行为，没有截图就没有闭环。
- 最稳的交付方式是：**功能一遍过 + 视觉一轮校准**。这比“盲目一次成型”更可靠，也更省服务器时间。
