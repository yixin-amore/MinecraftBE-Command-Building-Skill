## 8. 断链：让不该跑的方块真的不跑

> ⚠️ **本章 2026-11 定稿（前后推翻过两次，以这一版为准）**
>
> - 第一版写「只有改朝向一种、`conditional_bit` 一律 0」→ 漏了要有条件位，**每刻空跑一条 setblock**
> - 第二版写「检测之后全部有条件」→ 业务块互相连坐，**一条失败后面全死**
> - 第三版写「自断块放链尾」→ 业务长度一变就得重算朝向，`=4` 反复算错
> - **现在（第四版，已实测通过）**：`[0]` 检测 → `[1]` 连接块**有条件** → `[2]` 重置块 → `[3..]` 业务**全部无条件**

### 8.0 三种做法对照

| 类型             | 原理                          | 空闲开销    | 粒度    | 用不用                     |
| -------------- | --------------------------- | ------- | ----- | ----------------------- |
| **三段式 + 改朝向** | 连接块有条件（接通），重置块自断，外部改朝向断开，业务全无条件 | **检测数** | 单条功能链 | ✅ **默认**（8.0.1）         |
| 全条件位级联         | 检测之后全部有条件，检测失败全跳过           | 检测数     | 单条功能链 | ⚠️ 变体，**业务块会连坐**（8.3.5） |
| **红石启停**       | 循环块 `auto=0`，不被激活           | **0 条** | 整个系统  | ✅ 可用（总开关，8.1）           |

### 决策树

```
需要一个总开关（整个系统停掉）？ → 是 → 再叠一层红石启停（0 开销）
   └ 否 → 按功能拆链，每条链 = 1 检测 + 1 连接 + 1 重置 + 若干无条件业务
            └ 还想更细的分段？ → 拆成更多链，一条链只放一个检测
```

**两层可以叠加**：

```
红石启停管"整个系统开不开"（0 条）
  └ 三段式管"每条功能链跑不跑"（检测块数）
```

### 8.0.1 默认做法：按功能分链 + 三段式

**先把命令按功能拆成若干条独立链，每条链配一个循环检测块 + 连接块 + 重置块。**
完整格式与硬规矩见 **8.0.2**（唯一权威），这里只讲"怎么拆"。

```
空闲每刻执行条数 = 功能链数
```

```
[0]    rep_*   cond=0   execute if entity <检测条件>                              ← 检测
[1]    chc_*   cond=1   setblock ~1 ~ ~ chain_command_block["facing_direction"=5]  ← 连接
[2]    ch_*    cond=0   setblock ~ ~ ~ chain_command_block["facing_direction"=4]   ← 重置
[3..]  ch_*    cond=0   <业务>
```

**断链成立的三步**：

1. 检测失败 → 连接块（`cond=1`）被跳过 → 重置块没人触发 → 它保持朝西（断开）
2. 下一格朝的是别处 → 再后面的块**根本不被触发**（不是"执行了但失败"，是压根没激活）
3. 空闲每刻只有检测 1 条在跑，`setblock` 一次都不发生

#### 检测怎么写

| 检测   | 命令                                                                               | 用途        |
| ---- | -------------------------------------------------------------------------------- | --------- |
| 恒真   | `execute if entity @a`                                                           | 时钟链 —— **这种要编译成常驻链，不插连接/重置块** |
| 持物   | `execute if entity @a[hasitem={item=fishing_rod,location=slot.weapon.mainhand}]` | 状态链       |
| 计分   | `execute if entity @a[scores={tg_reload=1..}]`                                   | 事件链       |
| 实体存在 | `execute if entity @e[type=xp_orb,tag=tg_bullet]`                                | 弹道链       |

❗ 检测**只负责"判"**，不带 `run`；连接块负责"接"，重置块负责"断"。

#### 断开怎么写（在链外面）

```
# 面板按钮 / 另一条链 / 玩家触发
setblock ~1 ~ ~-5 chain_command_block["facing_direction"=4]
```

打的是 **`[1]` 连接块**（不是 `[2]` 重置块——它会被连接块每刻摆正，打它等于没断）。
把连接块摆朝西 → 它指不回 `[2]` → 链物理断开。按「接通」把它摆回 `=5` 才恢复。

❗ **坐标必须用相对写法**（`~dx ~ ~dz`）。结构文件粘到别处时世界坐标会整体平移，
写死绝对坐标（`setblock 2 -60 7 ...`）粘完就指向空气，断链面板当场失效。
生成器里用 `{T:<链ID>:<索引>}` 占位符，构建时自动换成相对坐标（见 5.6）。

❗ **不要再包一层 `execute unless entity ... run`**：

```
✅  setblock ~1 ~ ~-5 chain_command_block["facing_direction"=4]
❌  execute unless entity @e[type=fishing_hook] run setblock ~1 ~ ~-5 chain_command_block["facing_direction"=4]
```

第二行不但没必要，还会把「断开」变成「没有子弹时才断开」——子弹一飞，
链就被连接块接回去，面板看起来完全没反应。

### 8.0.2 标准断链格式（唯一权威 · 照抄这一段）

> 用户 U3 定稿，2026-11 三次修订。**第三次就是「三段式」**：
> 检测 → 连接 → **重置**，重置块在**连接块的下一条**，不在链尾（U24）。
> **不要再自创写法**——前后在断链上翻车五次，全是没照这个格式。

一条可断链的功能链，方块序列**只能**是这三段（**朝向数字照抄，不要"聪明地"改成别的**）：

```
[0]      无条件   execute if entity <选择器>                                    ← 检测
[1]      有条件   setblock ~1 ~ ~ chain_command_block["facing_direction"=5]     ← 连接
[2]      无条件   setblock ~ ~ ~ chain_command_block["facing_direction"=4]      ← 重置
[3..]    无条件   <业务命令>
```

❗ **`=5` 和 `=4` 是字面要求**，不是"按几何算出来大概这个方向"。
`check_chain_break.py` 里已经把这两条字符串写死成 `CONNECT_CANON` / `RESET_CANON`，
差一个字符就报错。

#### 为什么三段式一定成立（朝向在触发那一刻就定了）

```
检测通过 → [1] 把 [2] 摆成朝东(5) → [1] 沿自己的朝向(东)触发 [2]
        → [2] 执行，把自己摆成朝西(4) → 本刻 [3..] 照跑（触发关系已定，改朝向不影响本刻）
        → 下一刻：[1] 又把 [2] 摆回朝东，重新接上
检测不通过 → [1] 是有条件块，被跳过 → [2] 没人触发 → 业务一条都不跑
```

**关键在"朝向快照"**：命令方块执行完自己的命令后，是沿它**进入执行时**的朝向找下一格。
[2] 执行时把自己摆成朝西，只影响下一刻，本刻照样把 [3] 带起来。
`cbc.py` 的模拟器就是这个语义（`fd_before = b.fd` 必须在跑命令之前取）。

#### 为什么重置块必须紧跟连接块，而不是放链尾（U24）

两个理由，第二个是硬的：

1. **语义**：重置块是"每刻把断点重置为断开"，连接块在检测通过时接回去。它是一对，
   摆在一起才好读。
2. **几何**：`[0] [1] [2] [3]` 全在第 0 行，蛇形第 0 行**恒朝东**，所以
   `[1]` 的 `~1 ~ ~`（东）和 `[2]` 的 `=4`（西 = 朝后）**永远成立，不用补齐**。
   放链尾就得算"朝后"是西还是南/北，之前为此补过一堆空命令，还反复算错。

| #       | 方块                            | 条件位   | 要求                                              |
| ------- | ----------------------------- | ----- | ----------------------------------------------- |
| `[0]`   | 循环块 `repeating_command_block` | **0** | 只判不跑，命令必须是 `execute if entity <选择器>`，不带 `run`    |
| `[1]`   | 链块 `chain_command_block`      | **1** | **全链唯一的有条件块**；`auto=1`；只写一句 `setblock`          |
| `[2]`   | 链块                            | **0** | **重置块**：紧跟连接块，把自己摆成朝后                        |
| `[3..]` | 链块                            | **0** | 业务，全部无条件，一条失败不连坐                                |

外部断开（面板 / 另一条链）打的是 **`[1]` 连接块**：

```
无条件  setblock <连接块相对坐标> chain_command_block["facing_direction"=4]
```

把连接块摆朝后，它就指不回 `[2]` 了 —— 业务停，而且**不会被 `[1]` 自己重新接上**
（`[1]` 的命令改的是 `[2]`，不是它自己），所以断开是稳定的，按「接通」才恢复。

五条硬规矩：

1. **`[1]` 必须是有条件块**。命令内容写对但方块 `conditional_bit=0` = 检测形同虚设，
   每刻白跑一条 `setblock`，业务照跑（用户两次点名）。
2. **`[2]` 必须在 `[1]` 的下一条**，不许放链尾（U24）。
3. **`[3..]` 必须全部无条件**。给业务块加条件位 = 一条 `damage` 没打中，后面整段瘫痪。
4. **断开只写一句 `setblock`**，不包 `execute unless entity ... run`，不用绝对坐标。
5. **`execute if entity @a` 这类恒真闸门直接删掉**，那条链编译成常驻链（见下）。

#### 例外：恒真闸门 —— 删掉闸门，直接循环

```
[0]   循环块  cond=0   <业务第一条>
[1..] 链块    cond=0   <业务>
—— 没有检测、没有连接、没有重置
```

`execute if entity @a` 每刻都成功，它当闸门毫无意义：重置块每刻白跑一条 `setblock`，
这条链也从不进「断开/接通」面板。**把闸门整条删掉**，循环块直接装第一条业务。

- 编译器：`cbc.Program.chain(..., loop=True)` → `kind="repeat"`
- 底层生成器：`gate_mode="loop"`

#### 验收（自动）

```
python scripts/cbc.py                                    # 编译器 + 模拟器自检（12 项）
python scripts/check_chain_break.py out/cb.json --expect 6
```

`check_chain_break.py` 沿 `facing_direction` 走每条链，逐格核对：

- 检测块是循环块、`cond=0`、**不许是 `@a`**
- `[1]` 是连接块、`cond=1`、`auto=1`、字面 `=5`
- `[2]` 是重置块、`cond=0`、字面 `=4`、**位置就在 `[1]` 的下一条**
- `[3..]` 没有一条 `cond=1`；链尾**不该**再有老的自断块
- 面板「断开」「接通」各 N 条、全是相对坐标、没有一条包 `execute unless`

### 8.0.4 链路排查：给每段加「听得见的标记」

「没反应」最难查的原因是**不知道停在哪一步**。做法：在关键链的最前面各塞一组
**无条件**的「响一声 + actionbar 闪字」，它们不依赖任何计分项：

```
# 扳机链最前面（钩子一出现就响）
execute at @e[type=fishing_hook] as @p run playsound random.orb @s ~ ~ ~ 1 2
execute at @e[type=fishing_hook] as @p run titleraw @s actionbar {"rawtext":[{"text":"§b▷ 扳 机"}]}

# 开火标置上之后（条件都过了）
execute as @a[scores={tg_fire=1}] run titleraw @s actionbar {"rawtext":[{"text":"§a◈ 开 火"}]}

# 出弹链最前面
execute as @a[scores={tg_burst=1..}] at @s run playsound random.bow @s ~ ~ ~ 1 1.2
execute as @a[scores={tg_burst=1..}] run titleraw @s actionbar {"rawtext":[{"text":"§e▸ 出 弹"}]}
```

判读：

| 现象 | 结论 |
| --- | --- |
| 抛竿什么都没听到 | 钩子没被识别 / 那条链根本没跑（先查检测块） |
| 听到「扳机」没看到「开火」 | 开火条件没过：冷却 / 换弹中 / 空仓 |
| 看到「开火」没听到「出弹」 | `tg_burst` 没置上（`tg_type` 是 0 或缺项） |
| 三个都过了但没弹道 / 没伤害 | 载体召唤 → 打标 → 灌参数，逐段查（A20 就是这一段） |

再加一个**试射按钮**（直接 `tg_burst=1` 跳过扳机）和一个**自检按钮**（打印全部计分项），
三件套齐了就不用靠猜。

### 8.0.3 编译器 `cbc`：写程序，不写命令

> 用户 U18：「新的逻辑不是单纯的写指令，而是编程语言转指令」。
> 断链翻车四次的根因不是不会写，是**结构藏在几百条字符串里**，改一次漏一次。

`scripts/cbc.py` 把「链的结构」从业务里剥出来：**你只写业务，编译器排检测/连接/重置/条件位。**

```python
import cbc

p = cbc.Program("潮汐鱼竿枪")
p.chain("state", body, when="@a[hasitem={item=fishing_rod,location=slot.weapon.mainhand}]")
p.chain("clock", body, loop=True)          # 恒真链：没有检测/连接/重置
p.chain("init",  body, impulse=True)       # 面板：脉冲块 + 按钮
system = p.emit()                          # 直接喂给 build_cbworld
```

| 链类型 | `compile()` 产出 | 方块序列 |
| --- | --- | --- |
| `when="选择器"` | `kind="gated"` | 检测 / 连接 / **重置** / 业务 |
| `loop=True` | `kind="repeat"` | 循环块(装第一条业务) / 业务…（无检测无连接无重置） |
| `impulse=True` | `kind="impulse"` | 脉冲块(auto=0，等按钮) / 业务… |

三条断言（违反直接 `ValueError`，不让错误进产物）：

1. `when` 只写**选择器**，写了 `execute` 或 `entity ` 前缀就报错——防止拼出
   `execute if entity entity @a`（真踩过）。
2. `loop` 链不许带 `when`——那就是「没删掉 `execute if entity @a`」。
3. `impulse` 链不许带 `when` / `loop`。

#### 内置模拟器：先证明会跑，再生成

`python scripts/cbc.py` 跑 12 项自检，其中一项是**反例**：

```
✓ 检测恒通 → 业务每刻跑 1 次
✓ 检测第 3 刻起失败 → 业务停
✓ 第 4 刻外部断开 → 业务停
✓ 断开后再接通 → 业务恢复
✓ 反例：连接块没条件位 → 检测失败也跑     ← 「空转 / 检测形同虚设」
✓ 布局 [1] 是连接块（有条件）/ [2] 是重置块（无条件）/ [3] 起才是业务
✓ 常驻链没有检测字段 / 不带重置块 / 首块是循环块 / 每刻都跑
```

模拟器把编译产物摊成一条链，按「检测成功才传播、`cond=1` 依赖前一块成功、
`setblock` 改朝向、**朝向在触发那一刻快照**、每块每刻最多跑一次」逐刻推演。
**结构错在生成前就暴露，不用等进游戏。**

> ❗「朝向快照」是模拟器的关键语义，也是三段式成立的前提：
> 重置块执行时把自己摆朝西，只影响下一刻；本刻它仍按**进入执行时**的朝东方向
> 把业务带起来。模拟器里就是 `fd_before = b.fd` 必须在跑命令之前取。

#### 为什么必须分链，而不是在一条链里切多段

一条链只有**一个检测**。检测失败后，后面的块**全部**不执行，  
所以链内不存在"第二个开关"——想独立启停只能**再开一条链**。

```
想要 3 段独立控制 → 3 条链 → 3 条常驻
```

#### 实例：断链演示（39 个命令方块 / 2 条链 / 2 个有条件块）

| 链    | 格      | 条件位   | 命令                                                          |
| ---- | ------ | ----- | ----------------------------------------------------------- |
| A 检测 | x=0    | 0     | `execute if entity @a[tag=奖励]`                              |
| A 连接 | x=1    | **1** | `setblock ~1 ~ ~ chain_command_block["facing_direction"=5]` |
| A 重置 | x=2    | 0     | `setblock ~ ~ ~ chain_command_block["facing_direction"=4]`  |
| A 业务 | x=3..6 | 0     | 音效 ×2 / `give` / 清标记                                        |
| B 检测 | x=0    | 0     | `execute if entity @a[scores={奖励=1..}]`                     |
| B 连接 | x=1    | **1** | 同上                                                          |
| B 重置 | x=2    | 0     | 同上                                                          |
| B 业务 | x=3..6 | 0     | 音效 ×2 / `give` / 清零                                         |

`dump_cbworld.py` 输出 `条件位： {0: 37, 1: 2}` —— **`1` 的个数 = 功能链数**，这就是核对依据。  
面板上的「断开链条」按钮把两条链的 **x=1（连接块）** 改成朝西 —— 改成 x=2 会失效，
因为 x=1 每刻都会把 x=2 重新摆正（U24 的副作用，也是必须打连接块的原因）。

**链的顺序有意义**：`state` 算出来的 `tg_type` / `tg_mag`，`fire` 要用；  
`fire` 生成的子弹，`bullet` 要推进。按 z 从小到大排，就是执行顺序。

### 8.1 物理断链 · 红石启停（0 常驻）

#### 8.1.1 前提：`auto` 的语义

| `auto`                     | 行为        | 红石对它   |
| -------------------------- | --------- | ------ |
| `1`（始终活动 / Always Active）  | 放下就跑，不用信号 | **无效** |
| `0`（需要红石 / Needs Redstone） | 有信号才跑     | 有效     |

所以要做红石启停，**循环块必须先设成 `auto=0`**。  
默认生成器写的是 `auto=1`，要先改。

#### 8.1.2 接法一：红石块（推荐）

循环块旁边放一个红石块当常亮电源，用 `setblock` 在**红石块 / 空气**之间切换：

```
# 开
setblock 100 4 100 redstone_block
# 关
setblock 100 4 100 air
```

关掉后循环块**一帧都不执行**，整条链彻底停摆 → **空闲开销 0**。

红石块放在哪？**任意相邻格**都行（上下左右前后 6 面都吃）。  
推荐放在循环块的**背面**（与链条相反的方向），不挡视线。

#### 8.1.3 接法二：拆链首

直接把循环块换成空气，开的时候再放回去：

```
# 关
setblock 100 4 100 air
# 开（命令要一起写进 NBT）
setblock 100 4 100 repeating_command_block ["facing_direction"=5,"auto"=0b,"Command"="testfor @a"]
```


缺点：命令字符串极长，**方块一换状态就丢**（`SuccessCount`、`LastExecution` 全部清零）。  
只在接法一不可行时用。

#### 8.1.4 接法三：拉杆 / 按钮（手动）

玩家自己控制。拉杆放循环块旁边，`auto=0`，扳一下开、再扳一下关。  
适合"玩家可以自己关掉的模块"（HUD、自动战斗、提示音）。

❗ 按钮只给**一瞬间**的信号，循环块只会跑 1 刻就停。要持续跑必须用**拉杆**。

#### 8.1.5 三条红线

❗ **换方块类型不能每刻切换**。`setblock` 换 air / 换回命令方块会触发方块更新、  
光照重算、区块脏标记，而且 **NBT 全丢**，每刻改一次比一直跑还卡。  
只在"一次开关、长期不变"时用。

> ❗ **`setblock` 改朝向也不行**：只给方块状态会重建方块、清空方块实体。  
> 断链只用 `conditional_bit`（第 8 章），不需要任何 `setblock`。

❗ **不要用手持物品当开关**。手持状态每刻都可能变，等于每刻都在改方块。  
开关要由**面板按钮**（玩家主动按）驱动。

❗ **自检脚本读不到物理断链的效果**。静态回读只能验证"当前方块状态"，  
不能验证"运行时会怎样"。物理断链必须**游戏内实测**。

#### 8.1.6 面板按钮接法（最稳）

面板按钮（脉冲块）→ 改红石块。玩家自己按，不占常驻：

```
# 按钮「开启系统」
setblock 100 4 100 redstone_block
tellraw @p {"rawtext":[{"text":"§a系统已开启"}]}

# 按钮「关闭系统」
setblock 100 4 100 air
tellraw @p {"rawtext":[{"text":"§7系统已关闭"}]}
```

❗ 按钮本身在**脉冲链**上，只在按下的那一瞬执行一次，不占循环链开销。

### 8.2 朝向语义（摆链靠它，断链也靠它）

`facing_direction` 有**两个用途**：

1. **摆链**：链方块的朝向 = 它要触发的**下一格**方向。写错一格，链在那里就断了
2. **断链**：把连接块改成不指向下一格 = 物理断开；再改回来 = 接通

| `facing_direction` | 方向 | 向量   | 链上往哪走            |
| ------------------ | -- | ---- | ---------------- |
| 0                  | 下  | `-Y` | 断（指向地底，真实地图用它自断） |
| 1                  | 上  | `+Y` | 天然终点（末块用）        |
| 2                  | 北  | `-Z` | 蛇形反向行            |
| 3                  | 南  | `+Z` | 蛇形换行             |
| 4                  | 西  | `-X` | 蛇形反向行 / 断（反方向）   |
| 5                  | 东  | `+X` | 正向行              |

所以一条沿 `+X` 走的链，每块都朝 `5`；沿 `-X` 走的链，每块都朝 `4`。

**蛇形布局下每格朝向都不同**，必须由生成器按 `path[i+1] - path[i]` 现算，不能写死：

```python
def _fkey(dx, dz, cond=0):
    pre = "chc_" if cond else "ch_"       # 条件位只影响方块键，不影响朝向
    if dx > 0: return pre + "E"
    if dx < 0: return pre + "W"
    if dz > 0: return pre + "S"
    return pre + "N"
```

**末块一律朝上（`fd=1`）**——指向空气 = 天然终点，永不回指前一块。  
末块也要按条件位选键：无条件用 `ch_U`，有条件用 `chc_U`。

#### 三段式让"换行处"这个问题彻底消失

**连接块和重置块永远在前三格 → 永远在第 0 行 → 第 0 行恒朝东。**
所以 `~1 ~ ~`（东）和 `=4`（西 = 朝后）**字面写死就行，不用按 path 现算**。

这是三段式最实在的收益：老的四段式把自断块放在链尾，链尾落在哪一行由业务长度决定，
换行处"朝后"可能是南/北，于是要按 `path` 现算朝向 —— 算错一次就整条链断掉，
而且会写出 `=2`/`=5`，和用户要的字面 `=4` 对不上。

```
✅ 三段式：连接块 ~1 ~ ~ =5 / 重置块 ~ ~ ~ =4      ← 字面写死，前三格恒在第 0 行
❌ 四段式：自断块放链尾 → 得按 path 算"朝后"       ← 已废弃（U24）
```

> 只有**老的 `{CUT}` 占位符**（`build_cbworld` 为旧 spec 保留）才需要按几何算，
> 新代码一律走 `{RESET}`，`_self_reset()` 里带几何断言：不在朝东行上直接报错。

### 8.3 条件位的确切语义（只有连接块用它）

#### 8.3.1 两种方块的行为

| 方块类型                   | 行为                  |
| ---------------------- | ------------------- |
| **无条件**（Unconditional） | 前一块**执行了**就跑，不管成不成功 |
| **条件**（Conditional）    | **仅当前一块执行成功时**才跑    |

关键区别只有一条：

```
前一块「执行了但失败」  → 无条件块照跑；条件块跳过
前一块「根本没执行」    → 两者都不跑（链断了，触发不到）
```

**这正是三段式断链成立的根据**：检测失败 → 连接块（条件）跳过 → 连接块**没执行** →
重置块**根本不被触发** → 业务块一条都不跑，与它们有没有条件位无关。

#### 8.3.2 检测写法

一条**以 `if` / `unless` 结尾、没有 `run` 的 `execute`**：

```
execute if entity @a[scores={slash_t=1..}]
execute if entity @a[hasitem={item=blaze_rod,location=slot.weapon.mainhand},scores={energy=40..,burst_cd=0}]
execute if score #tick sys matches 20..
execute if entity @a
```

- 命中 → 返回成功 → 连接块（条件）执行 → 链接通
- 未命中 → 返回失败 → 连接块跳过 → 链断开

❗ 检测要**尽量便宜**：`if entity` 带 `scores`/`hasitem` 比 `execute as @a run ...` 便宜得多，
因为它不做任何写入。

❗ **检测里不要塞 `hasitem` 当"保险"**：一不匹配整段静默跳过，排查时看不到任何反馈。
能用别的方式证明前提（例如"钩子存在就说明有人抛竿"）就别加 `hasitem`（U26 / A21）。

#### 8.3.3 指标与公式

**唯一指标：空闲时每刻执行的条数 = 循环闸门数。**

```
空闲开销 = 输入通道数 + 定时器数        目标 ≤3
```

| 手段          | 说明                                   |
| ----------- | ------------------------------------ |
| **输入通道当闸门** | 一个"玩家做了什么"的检测一个闸门                    |
| **定时器降频**   | `#tick += 1` + `matches 20..`        |
| **总闸门**     | 纯数据系统用 `execute if entity @a` 顶第一个通道 |
| **剪冗余**     | 重复的状态维护、算了不用的中间量，全删                  |

#### 8.3.4 硬定律：N 个互斥分支 = N 条链

**任何写法都压不下去。**

Bedrock 选择器**不支持 OR**，`hasitem` 一次只能测一个物品；  
一条链只有一个闸门，A 分支不成立时整条链都不跑，B 分支没地方待。

所以"把多个分支塞进一段" = 丢功能。反例：

```
[闸门] execute if entity @a[scores={slash_t=1..}]
[业务] slash=1 的 7 个粒子点
[业务] slash=2 的 7 个粒子点   ← slash=1 没人时，这 14 条一条都不被触发
[业务] slash=3 的 7 个粒子点
[业务] slash=4 的 8 个粒子点
```

正确：**每个形态一条链**（各带自己的检测 + 连接 + 重置）。

#### 8.3.5 变体：全条件位级联（能用，但会连坐）

把连接块去掉，改成"检测之后全部 `conditionalMode=1`"：

```
[0]   循环闸门   无条件
[1..] 业务       全部有条件
```

|               | 单条件位 + 改朝向（默认） | 全条件位级联（变体）                  |
| ------------- | -------------- | --------------------------- |
| 空闲开销          | 闸门数            | 闸门数                         |
| 需要 `setblock` | 每链 1 条复位       | **0 条**                     |
| 业务块互相影响       | **无**          | **一条失败，后面全死**               |
| 排错难度          | 低（业务块各自独立）     | 高（要看前一条成不成功）                |
| 适合            | 绝大多数系统         | 业务块本身都带 `execute if`、失败概率极低 |

**连坐的典型事故**：段内第一条是 `damage @e[r=3.5]`，范围内没敌人 → 失败 →  
后面的攒能量、连招推进、刀光设置全部跳过 → 整个战斗系统瘫痪。  
用单条件位就没有这个问题：`damage` 失败只是它自己没生效。

> 潮汐鱼竿枪 v3 用的是这个变体（300 个条件块）。它每条业务命令都自带  
> `execute as @e[...] run`，失败概率低，所以能跑；但**重建时建议改成单条件位**。

### 8.4 业务块的排序铁律（用变体时必读）

全条件位变体下：**段内任何一条失败，后面的全死**。这不是缺陷，是级联的原理；  
但排错顺序写反，就会把功能"静默吃掉"。用默认的单条件位方案时，这一节可以跳过。

#### 8.4.1 按"存活优先级"排序

| 顺序 | 类型                                                         | 会不会失败      |
| -- | ---------------------------------------------------------- | ---------- |
| 1  | `scoreboard set/add/remove/operation @a ...`（不带 scores 过滤） | 有人就成功      |
| 2  | `execute as @a run scoreboard ...`                         | 有人就成功      |
| 3  | `particle`（固定坐标）                                           | 几乎不失败      |
| 4  | `execute as @a[scores=...] run ...`                        | **无目标就失败** |
| 5  | `playsound` / `damage` / `titleraw`                        | **最容易失败**  |

反例：段内第一条就是 `damage @e[r=3.5]`，范围里没敌人 → 失败 →  
后面的攒能量、连招推进、刀光设置全部跳过 → 整个战斗系统瘫痪。

#### 8.4.2 复位命令放段首

段末的复位（`#tick` 归零）如果放在最后，前面一条 `titleraw` 失败  
（比如刚好没人）就永远不归零，计数器一直涨到溢出。

```
[闸门] execute if score #tick sys matches 20..
[条件] scoreboard players set #tick sys 0        ← 复位放第一
[条件] execute as @a run titleraw @s actionbar ...  ← 易失败的放后面
```

#### 8.4.3 把"会失败"降级成"必成功"

带 `scores` 过滤的递减会失败：

```
scoreboard players remove @a[scores={atk_cd=1..}] atk_cd 1      ← 没人匹配就失败
```

改成**无条件递减 + clamp**：

```
scoreboard players remove @a atk_cd 1
scoreboard players operation @a atk_cd > zero sys      ← max(atk_cd, 0)
```

两条都必定成功（只要有人）。判定时用 `atk_cd=0` 而不是 `=..0`。

**用乘法代替条件清零**（连招窗口到期）：

```
scoreboard players operation @a combo_alive = @a combo_t
scoreboard players operation @a combo_alive < one sys     ← min(combo_t, 1) → 0 或 1
scoreboard players operation @a combo *= @a combo_alive   ← 窗口过期自动乘 0
```

三条纯算术，零失败风险。

### 8.5 降频定时器（这个可以用）

不是所有事都需要每刻做。**降频是唯一"花 2 条换几十条"的买卖**。

```
[闸门] execute if score #tick sys matches 20..    ← 常驻 1 条
   [条件] 复位、HUD、经验条、等级、击杀奖励、建档 ……   ← 四十多条，每秒才跑一次
```

前提是**得有人推这个计数器**（再花 1 条）：

```
scoreboard players add #tick sys 1
```

所以定时器的真实成本是 **2 条**。把它放进总闸门后面，无玩家时连计数器都不跑：

```
[循环块 = 总闸门] execute if entity @a
   [条件] scoreboard players add #tick sys 1        ← 有人才走表
   [条件] ……每刻必须的 10 条……
[闸门] execute if score #tick sys matches 20..
   [条件] scoreboard players set #tick sys 0        ← 复位放段首
   [条件] ……每秒的 40 条……
```

| 频率         | 放什么                     | 判据          |
| ---------- | ----------------------- | ----------- |
| 每刻（20/s）   | 伤害差值检测、受伤窗口倒计时          | **漏一帧就出错**的 |
| 每秒（1/s）    | HUD 刷新、经验条、等级判定、奖励结算、建档 | 慢 1 秒玩家察觉不到 |
| 每 4 刻（5/s） | 血条平滑动画、冷却显示             | 纯视觉         |

**反例**：给每一段都加 `matches 20..` 前缀（老写法），  
40 条就变 40 个方块 + 40 条每刻执行。改成"1 个闸门 + 40 条条件块"，  
每刻执行从 40 降到 1。

### 8.6 两层组合方案（实战）

一个完整副本系统的断链设计：

```
【第一层 · 红石启停】循环块 auto=0，旁边红石块
   → 副本没开始时，整个系统 0 开销
   → 玩家踩压力板 / 按面板按钮 → setblock 红石块 → 系统启动

【第二层 · 三段式】副本内部按功能拆成四条链
   ├ 时钟链（闸门恒真）
   ├ 状态链（有人持武器时）
   ├ 奖励链（有奖励标记时）
   └ 结算链（有结算标记时）
   每条链 = 1 检测（无条件）+ 1 连接（有条件）+ 1 重置（无条件）+ 若干无条件业务
```

开销：

| 状态         | 每刻执行          |
| ---------- | ------------- |
| 副本没开始      | **0 条**（红石断开） |
| 副本进行、无人持武器 | 4 条（四个闸门）     |
| 战斗中        | 4 条 + 该链业务    |

### 8.8 断链的验证方法

#### 8.8.1 脚本回读：数有条件块

`dump_cbworld.py` 直接打印条件位分布，一眼就能对：

```
条件位： {0: 37, 1: 2}       ← 1 的个数 = 功能链数（断链演示：2 条链 = 2）
TrackOutput： {1: 39}        ← 全 1 = 方块界面「上一个输出」都保留
```

判据：

| 现象             | 说明                |
| -------------- | ----------------- |
| `1` 的个数 = 功能链数 | ✅ 正确（每条链 1 个连接块）  |
| `1` 的个数 = 总块数  | ❌ 全条件位变体，业务块会连坐   |
| `1` 的个数 = 0    | ❌ 根本没断链，每刻全部方块都在跑 |
| `1` 的个数 > 功能链数 | ❌ 有业务块误加了条件位      |

再沿 `facing_direction` 走一遍，确认 `[1]` 有条件位、`[2]` 是字面 `=4`：

```python
DIR = {0:(0,-1,0), 1:(0,1,0), 2:(0,0,-1), 3:(0,0,1), 4:(-1,0,0), 5:(1,0,0)}
cur, i, seen = repeating_block_pos, 0, set()
while cur in grid and cur not in seen:
    seen.add(cur)
    if i == 1 and not grid[cur].conditional_bit:
        print("第 1 格不是有条件块 → 检测失败时连接块仍会跑，白花一条 setblock")
    if i == 2 and grid[cur].command != 'setblock ~ ~ ~ chain_command_block["facing_direction"=4]':
        print("第 2 格不是字面 =4 的重置块 → 断链不成立")
    cur = (cur[0] + DIR[grid[cur].facing][0], ...)
    i += 1
```

**别自己写这个脚本**——`scripts/check_chain_break.py` 已经做了，而且把两条命令
写成 `CONNECT_CANON` / `RESET_CANON` 常量逐字符比对：

```
python scripts/check_chain_break.py out/cb.json --expect 6
```

输出长这样（每条链一行，全 ✓ 才算过）：

```
  ✓ [常驻] tick       3 格
  ✓ [可断] ready      19 格
  ✓ [可断] cooldown   64 格
  ...
可断链 6 条（期望 6）/ 常驻链 1 条 / 面板链 8 条
面板 setblock（断开+接通）12 条（期望 12）
结论：通过
```

#### 8.8.2 游戏内实测

静态脚本验证不了"运行时会怎样"，只能进游戏看：

| 检查    | 怎么看                          |
| ----- | ---------------------------- |
| 检测失败  | 后面方块**完全没有执行记录**（「上一个输出」不刷新） |
| 连接块生效 | 按「断开链条」后链不跑；再按「接通」，链自动恢复     |
| 红石启停  | 拆掉红石块，看「上一个输出」是否停止更新         |

#### 8.8.3 自查清单

1. 每条 gated 链第 0 格是循环块，且 `conditionalMode=0`、命令是 `execute if entity ...`？
2. 第 1 格是连接块，`conditionalMode=1`，字面 `=5`？
3. 第 2 格是重置块，`conditionalMode=0`，字面 `=4`，**紧跟第 1 格**？

### 8.9 什么时候不该断

| 场景                                                   | 要不要断                |
| ---------------------------------------------------- | ------------------- |
| 循环链超过 30 个方块                                         | **必须**（逻辑）          |
| 链里有 `particle` / `damage` / `playsound` / `titleraw` | **必须**（逻辑）          |
| 只在特定状态才需要的逻辑                                         | **必须**（拆成独立链 + 连接块） |
| 有系统总开关                                               | **必须**（红石）          |
| 初始化链（脉冲 + 按钮）                                        | 不用（只跑一次）            |

## 58. 断链的工程落地

前面第 8 章讲了原理，这里讲**怎么在生成器里落地**。

### 58.1 spec 写法

```json
{"id": "tick", "kind": "repeat", "button": false,
 "segments": [
   {"gate": "execute if entity @a",
    "cmds": ["...每刻..."]},
   {"gate": "execute if score #tick sys matches 20..",
    "cmds": ["scoreboard players set #tick sys 0", "...每秒..."]},
   {"gate": "execute if entity @a[hasitem={item=iron_sword,location=slot.weapon.mainhand}]",
    "cmds": ["...持剑时..."]}
 ]}
```

`expand_segments()` 展开成 `[(命令, 是否条件)]`：

```python
def expand_segments(seg_list):
    out = []
    for seg in seg_list:
        gate = seg.get("gate")
        if gate:
            out.append((gate, False))       # 闸门必须无条件
        out.extend((c, True) for c in seg["cmds"])
    return out
```

### 58.2 布局时写 `conditional_bit`

```python
def _key(d, cond):
    return d.replace("ch_", "chc_") if cond else d
```

- 条件块：`chain_command_block` + `conditional_bit=1`
- 无条件块：`conditional_bit=0`
- 末块沿用本行流向

❗ `chc_E/W/S/N` **四个朝向都必须有**。只做朝东一种，蛇形反向行会全部错位。

### 58.3 生成时打印常驻比

```
主循环 56 块，常驻 2 块（3.6%），空闲时只有这 2 条在跑
```

**别靠猜，靠打印。**

### 58.4 验证：从文件回读

```python
DIR = {0:(0,-1,0), 1:(0,1,0), 2:(0,0,-1), 3:(0,0,1), 4:(-1,0,0), 5:(1,0,0)}
rep = 找 repeating_command_block
cur, idle, clen, seen = rep, 0, 0, set()
while cur in grid and cur not in seen:
    seen.add(cur); clen += 1
    if not grid[cur].conditional_bit:
        idle += 1                      # 无条件块 = 每刻必定执行
    cur = (cur[0] + DIR[facing][0], cur[1] + DIR[facing][1], cur[2] + DIR[facing][2])
```

判据：

- 常驻 = 0 → 连循环块都是条件块，链根本不会启动
- 常驻 > 3 且不是多通道系统 → 有"每刻必跑段"没拆掉

## 66. 断链：真实地图的三种做法

### 66.1 `setblock` 改朝向（和本 skill 完全一致）

```mcfunction
# 指令区 999，原样
execute as @a[tag=购买] run setblock ~~~1 chain_command_block 3
# 指令区 −10000，原样（连接块朝运行方向，不带 NBT → 内容不丢）
execute unless entity @a[tag=升级天赋] run setblock ~~~ chain_command_block 0
```

**真实地图确实在用"不带 NBT 的 setblock 只改状态"这个特性。** 本 skill 的做法不是发明，是提炼。

> 关键细节（第 8 章）：这条 `setblock` **在链里必须是有条件块**。
> 真实地图把它包在 `execute ... run` 里，本质也是"只有条件成立才动方块"。
> 写成无条件 → 闸门失败也每刻复位一次，白花一条 `setblock`。
>
> 另外注意它改的是**同类型**（`chain_command_block` → `chain_command_block`），
> 只换 `facing_direction`。换成 `air` 或别的类型就会重建方块、擦掉 NBT。

### 66.2 `auto=0` + 红石（大规模用）

指令区 999 的 229 个循环块里 **219 个 `auto=0`**——平时不跑，踩压力板/按按钮才激活。  
配合软检测：

```mcfunction
execute unless block ~-1 ~1 ~1 redstone_block if entity @a[hasitem=…] run …
```

**这就是"物理断链"在真实地图里的规模**：0 空闲开销，靠红石。

### 66.3 末块朝上 = 天然终点 ★

弗拉迪的链末块写的是 **`facing_direction=1`（朝上）**：

```
… (24,-59,0) fd=5 → (25,-59,0)  ← 没有方块，链自然停
… ( 1,-59,1) fd=1 → ( 1,-58,1)  ← 朝上，指向空气，绝不回指
```

**好处**：朝上永远不会指回前一块，天然不可能自触发。  
**代价**：不能断链（已经断了）。

> **给生成器的建议**：末块用 `fd=1`（朝上）比"沿用流向"更安全。  
> 沿用流向在拐弯处一旦算错就指回前块 → 死循环。朝上只有"停"一种结果。
