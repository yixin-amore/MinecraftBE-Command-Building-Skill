# 多思考、联动、创造性：设计前的思考协议

> 目标不是“想得多”，而是**在想清楚之后少返工**。
> 每次接到“设计一个 Boss / 系统 / 地图 / 菜单”，先走完这份协议，再写命令。

## 1. 先想三件事

1. **玩家在做什么？** 操作、决策、失败、重试。
2. **玩家看到什么？** 轮廓、颜色、UI、镜头、音效、节奏。
3. **服务端在跑什么？** 实体、命令、计分板、区块、刷新频率。

如果三件事对不上，设计一定返工。

## 2. 思考预算

| 阶段 | 占比 | 产出 |
|---|---:|---|
| 想 | 30% | 目标/约束/3 个方向/风险 |
| 做 | 50% | 最小闭环 + 数据表 + 命令 |
| 测 | 20% | 单机制/多人/性能/重置 |

不要 0% 想、100% 堆命令。

## 3. 每次先问 6 个问题

- 玩家为什么想玩这个？一句话的“幻想”是什么？
- 最小可玩闭环是什么？只保留一个核心机制能不能成立？
- 它和现有系统怎么联动？能复用哪些状态/菜单/经济/UI/建筑？
- 约束是什么？版本、区块、实体上限、命令长度、网易边界。
- 最可能怎么坏？多人、卡顿、误判、逃课、看不懂。
- 怎么证明它成立？一个 30 秒测试 / 一张截图 / 一条日志。

## 4. 先发散，再收敛

每次至少给 **3 个方向**，不要第一个念头就开工：

| 方向 | 目标 | 例子 |
|---|---|---|
| 稳健 | 低风险、可落地 | 现有 Boss + 一个新技能 |
| 联动 | 两个系统咬合 | FMBE 模型 + 数据化护盾 + 场地机制 |
| 大胆 | 记忆点/奇观 | 阶段转换时竞技场塌陷/换形态 |

然后用 **6 维评分** 选一个：

| 维度 | 问题 |
|---|---|
| 新鲜感 | 和服务器现有内容像不像？ |
| 一致性 | 和世界观/美术/节奏一致吗？ |
| 可落地 | 命令方块/FMBE/建筑能做吗？ |
| 性能 | 实体/命令/粒子/区块撑得住吗？ |
| 可读性 | 玩家 3 秒内看懂吗？ |
| 可测试 | 能单独验证吗？ |

## 5. 联动矩阵：不要孤立做系统

把设计拆成 8 层，逐层找“能不能咬合”：

| 层 | 可联动 |
|---|---|
| 触发 | 雪球/鸡蛋/纸/钓鱼钩/触摸点/按钮 |
| 状态 | 计分板、tag、阶段、冷却、UID |
| 数据 | 生命/护盾/攻击/防御/暴击/经验/金币 |
| 表现 | actionbar 血条、title、粒子、音效、camerashake |
| 空间 | 竞技场、掩体、高低差、传送点、塌陷 |
| 成长 | 等级、天赋、装备、词条、商店 |
| 社交 | 组队、匹配、排行榜、工会、领地 |
| 保护 | 反作弊、领地、封禁、回滚、重置 |

**联动不是“功能多”，而是“一个系统的输出成为另一个系统的输入”。**

例子：

- 雪球菜单 → 数据化个人面板 → 商店/签到 → 金币后处理。
- Boss 护盾 → 破盾 → 阶段转换 → 场地塌陷 → 新技能。
- 触摸检测 → 菜单选择 → 小游戏判定 → 排行榜。
- FMBE 模型 → 受击动画 → 血条变化 → 死亡掉落。
- 建筑竞技场 → 掩体/视线 → Boss 技能命中率 → 玩家走位。

## 6. 创造性技巧（约束内）

1. **SCAMPER**：替代/组合/借用/修改/放大/缩小/重排。
2. **反转**：Boss 被打会回血？护盾越打越硬？玩家必须不攻击？
3. **约束**：只用一个区块、只用 100 个方块、不用 camera。
4. **类比**：音游的节拍 → Boss 技能节奏；塔防的波次 → 小怪阶段。
5. **叙事**：场地先讲故事，Boss 再出场。
6. **奇观**：阶段转换换形态/换场地/换音乐。
7. **复用**：把已有菜单/商店/数据化当乐高，不重复造。

创造不是“加更多”，而是**用一个新连接让旧系统产生新玩法**。

## 7. 红队：先想怎么坏

- 多人：两个玩家同时触发会串吗？
- 性能：20 Hz 长链/大量实体/粒子会卡吗？
- 逃课：卡视角、卡距离、卡阶段、刷物品？
- 误判：反作弊/命中/触摸坐标会误伤吗？
- 可读性：玩家知道现在该做什么吗？
- 重置：死亡/退出/重进能恢复吗？
- 兼容：网易 1.21.130 的命令都在吗？

每个风险写一句“如果发生，怎么兜底”。

## 8. 最小闭环优先

先做：

1. 一个触发；
2. 一个状态；
3. 一个反馈；
4. 一个失败/重置。

跑通后再加第二个技能、第二阶段、第二套 UI。不要第一天就做“完整 Boss + 地图 + 经济 + 排行榜”。

## 9. 回答用户的格式

除非用户明确说“直接做”，否则先给：

```
1. 我理解的目标 / 约束 / 未知
2. 3 个方向（稳健 / 联动 / 大胆）
3. 推荐哪个，为什么
4. 系统联动图（触发→状态→数据→表现→空间→成长）
5. 最小可玩闭环
6. 风险与测试计划
```

确认后再开工；开工时先出**数据表/状态表**，再出命令。

## 10. 自检：这次有没有“多想一步”

- [ ] 我是否只给了第一个念头？
- [ ] 我是否复用了已有系统，而不是重复造？
- [ ] 我是否写了一个“联动”而不是“功能列表”？
- [ ] 我是否考虑了多人/性能/逃课/重置？
- [ ] 我是否能用一句话说清玩家在玩什么？
- [ ] 我是否先用最小闭环验证，再扩展？
- [ ] 我是否在开工前给了 3 个方向？

## 11. 本项目的联动样例

### Boss
FMBE 模型（轮廓/前摇） × 数据化（生命/护盾） × 阶段（100/60/30） × 场地（掩体/塌陷） × UI（10 段血条） × 掉落/经济。

### 雪球菜单
雪球触发 × 计分板页面 × actionbar UI × 数据化个人面板 × 商店/签到 × 权限/重置。

### 触摸小游戏
烟花触摸点 × 二分屏幕坐标 × 菜单按钮 × 判定区间 × 排行榜/奖励。

### 建筑
竞技场尺度 × 视线 × 掩体 × Boss 技能范围 × 玩家入口/退场 × 表演镜头。

> 联动的检验标准：拿掉其中一层，另外一层会明显变弱；否则它们只是拼在一起。
