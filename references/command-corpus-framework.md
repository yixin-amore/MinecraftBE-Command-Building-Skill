F 世界层：structure save/load、区块加载
G 性能层：分支预算、实体预算、刷新频率、生命周期

## 4. 跨文件模式

### 4.1 N 叉树是主线

`positioned`/`rotated`/`facing` 的大量出现，说明作者不是为每个点放一个命令方块，而是：

```text
根坐标 → 嵌套 rotated/positioned → 多个叶子动作
```

典型：

- 2D/3D 几何：`binaryTree2D/3D`
- 旋转圆：`rotatedCircle`
- 二分随机：`二分随机`
- 坐标序列：`noneEntity`

设计时先算**分支数**，再决定是否对称/预计算/降频。

### 4.2 实体是“锚点/显示器”

| 实体 | 用途 |
|---|---|
| boat `name=tree` | 空间旋转锚点/方向载体 |
| armor_stand `name=d`/`lt` | 圆/螺旋锚点、移动光源 |
| item | 像素/信号/显示 |
| fishing_hook | 玩家输入、投射物 |
| xp_orb | 子弹/特效载体 |
| leash_knot | 路径/碰撞探针 |
| ender_crystal/tnt | 爆炸/投射物 |

**规则**：逻辑状态放计分板；实体只做空间锚点/显示；用完 kill/清 tag。

### 4.3 物品数量数据化

`物品数量数据化.txt` 用大量 `hasitem` 数量条件把背包数量映射为分数；这是**查表编码**，不是读 NBT：

- 优点：纯选择器，服务端可用。
- 代价：条件多、每条都要扫背包；要控制频率/背包槽位。
- 变体：用不同物品/槽位编码多个维度。

### 4.4 UID / 所有权

鱼竿枪系列用 `UID` 把投射物绑定到玩家：

```text
hook → 玩家 → 生成子弹 → 子弹 UID = 玩家 UID → 后续只处理同 UID
```

关键：生成后立刻绑定；清理时按 UID/tag；避免多人串弹。

### 4.5 坐标序列 = 二进制分解

`noneEntity` 用：

```text
z += 8*1, 8*2, 8*4
x += 1*1, 1*2, 1*4
```

本质是**二进制位分解**：用 1/2/4 三个增量组合出 0..7 的偏移，少命令生成序列。  
这是“指令数学”的典型：把十进制坐标拆成二进制位。

### 4.6 JSON-Line 进度条

`Json-Line` 用嵌套 `translate/with` + `score` 选择器生成 50/100 段进度条，而不是每段一条命令：

- 优点：命令少、UI 连续。
- 代价：JSON 很长、可读性差；要配合 `titleraw`。
- 无障碍版把段数/颜色/文本编码到 `translate` 参数，便于本地化。

### 4.7 世界层：structure save/load

TNT 用 `structure save` 保存 TNT/实体，再用 `structure load` 回放：

- 适合一次性/短时回放；频繁 load 成本高。
- 需要区块加载；注意 `memory/disk` 和实体会被保存。
- 结束后清理模板实体。

## 5. 提炼出的设计规则

1. **先选层**：执行/空间/数据/实体/UI/世界，不要混在一条链。
2. **N 叉树先算分支预算**：分支数 × 叶子数 × 20 Hz。
3. **能对称就对称**：圆/球/星只算 1/4 或 1/2。
4. **能预计算就不现场算**：三角/曲线/坐标表。
5. **逻辑与显示分离**：分数/tag 做状态；实体只做锚点/像素。
6. **投射物必须有 UID/生命周期**：生成→绑定→检测→清理。
7. **UI 用编码而不是枚举**：JSON-Line 的 `translate/with` 比 100 条命令稳。
8. **坐标序列用二进制位分解**：1/2/4 组合，减少命令。
9. **所有临时实体有 kill/cleanup**：hook/xp_orb/tnt/armor_stand。
10. **区块加载是前提**：远处几何/回放必须 `tickingarea`。

## 6. 反模式

- 用 `#` 假玩家（网易报错）。
- 裸 `@e` 全图刷 N 叉树。
- 每个像素一条命令；应预计算/编码。
- `fill ... destroy` 让掉落物进入选择器，形成反馈。
- 投射物不绑定 UID，多人串弹。
- 只写生成不写清理，实体累积。
- 把 `item` 当唯一存储；区块卸载/合并会丢状态。
